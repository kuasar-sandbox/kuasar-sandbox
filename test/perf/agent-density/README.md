# Agent density: business-completion evidence

This tool **validates** a matched 3-concurrent vs 16-concurrent Agent experiment. It does not create MicroVMs, silently retry rejected tasks, or fabricate a static memory allocator. Capture each run with the prepared orchestrator E2E runner and retain its `summary.json`, `process-exit.json`, per-wave `timeline.jsonl`, environment/manifest, and raw process logs. The runner is currently a BMS test fixture, **not** a portable checked-in launch command; no `make perf` gate is claimed for it.

Run `python3 test/perf/agent-density/benchmark.py --fixed /path/to/fixed --density /path/to/density --output report.json` after copying evidence to a trusted analysis host. The checker rejects incomplete admission, incorrect task results, failed forwarding, OOM kills, failed cleanup, nonzero driver exits, and mismatched per-Agent peak/tool counts/output hashes. Compare fixed 3 and dynamic 16 with the same 24 or 48 task IDs, per-ID memory peaks and work. Keep zero business retries. The summary reports **sum of per-wave warmup + execution**; separately record the outer case wall clock (including setup/cleanup). This is a concurrency-controlled Kuasar comparison, **not** a comparison with Kubernetes or a distinct static memory manager.

Validated BMS experiment (2026-10-08): 8 vCPU/16 GiB host container, 12 GiB pool, 1 vCPU/4 GiB sandbox capacity, 256 MiB allocatable, 512 MiB startup, swap disabled. 24/48 agents completed on both x86_64 and arm64, with no business retries, host OOM kills, forwarding failures or remaining reservations. Peak simultaneous running was 16 for dynamic vs 3 for fixed. End-to-end case wall-clock (including setup/cleanup): 48 agents x86 1180 s fixed vs 432 s dynamic; ARM 1064 s vs 370 s. The full raw BMS evidence must be retained with version, exact binaries and host identity before treating these as a reproducible release baseline. These are **local workload-specific observations**, not general capacity guarantees.
